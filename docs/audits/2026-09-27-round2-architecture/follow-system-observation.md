# Follow system · English：gate16 限定观察

gate16 Standard 正式包中，原生设置选择「Follow system」后摘要为「Follow system · English」；同时只读 `persist.sys.locale` 为 `zh-CN`，系统 Files 等界面为中文。此前同一包名的 Low 进程曾选 English，覆盖安装 Standard 前又在原生页选 English。以上足以证实 DSHA 当前把 `system` 偏好解析成 `en`，但 **还不足以证实 Android 当前用户的实际系统 LocaleList 首项必为中文**：`persist.sys.locale` 可能不是该用户当前 configuration，Files 也可能有单独的应用语言。先保留为有可信产品缺陷迹象、来源待核实的设备观察；不据此宣称已修复或通过。

静态时序：`SettingsFragment` 的摘要来自 `ConfigStore.getUiLanguage()`，它对 `system` 调 `UiLanguagePreference.resolve(..., SystemLanguage.tag())`；所以当前摘要说明锁存的 tag 被判作非中文，而不只是旧 TextView。`DshaApp.onCreate` 在项目代码首次 `LanguageController.apply()` 前调用 `SystemLanguage.initialize()`，且项目没有 `attachBaseContext` 覆盖。`super.onCreate()` 之前的框架/Provider 初始化仍可能运行：合并后的 Standard manifest 有 AndroidX startup 的 Emoji、Lifecycle 和 ProfileInstaller provider，但未见项目 Provider 调用 `LanguageController`。`SystemLanguage.detect()` 反射读取 `Resources.getSystem().getConfiguration().getLocales().get(0)`，失败后取 `Configuration.locale`；两者都失败时 `tag()` 才回退 `Locale.getDefault()`。现有 JVM 测试只证实缓存后不会被后续 `Locale.setDefault` 改写，没有验证本机 Android 上首次捕获的来源。

有界假设是同包名 Low/Standard 保留的 Android per-app locale：`LanguageController.apply()` 不论偏好为显式 English 还是 Follow system，都调用 `AppCompatDelegate.setApplicationLocales` 写入 **解析后的** `en`；Android 13+ 可在下次进程创建前恢复该包的应用语言。若本机 ROM 把这个覆盖反映到 `Resources.getSystem()`，或反射探测失败而回退到已是英文的 `Locale.getDefault()`，首次锁存就会把应用语言误当系统语言，之后选择 Follow system 仍维持英文。该链在源码上可行，但目前没有进程初始化时的 `detect()` 实际返回值，不能把 ROM/反射分支说成已证实根因。

最短只读核对由持有设备的主代理在现有正式会话中完成，无需停 Web、强杀、清数据或安装测试包：读取当前用户的 **实际** Android global configuration/LocaleList（例如 `adb shell am get-config` 或 `dumpsys activity` 中 global configuration），再通过系统「应用语言」页或该 ROM 提供的只读 locale service 查询 `com.dsh.client` 的 per-app locale；同时保留当前 DSHA 设置摘要截图。若 global 首项确为 `zh` 而 DSHA 仍显示 Follow system · English，则需求违背已实证；per-app locale 为 `en` 将支持上述污染路径，但 `SystemLanguage.detect` 的具体分支仍需单独证据。若 global 首项实际非中文，则该次摘要符合当前解析规则。不要用 `persist.sys.locale` 一项或 Files 文案单独替代 global LocaleList。

后续只读确证：`adb shell am get-config` 首行含 `mcc460-mnc1-zh-rCN...v33`，`cmd locale get-app-locales com.dsh.client` 返回 `[en]`，原生设置仍显示 Follow system · English（私有 `standard16-system-language-restored.png`）。global configuration 中文、同包 per-app locale 英文、应用对「跟随系统」给出英文三点同时成立，D07 是已证实的产品缺陷；首锁污染的具体 `Resources.getSystem`/反射回退分支尚无需凭空指定。本机 SDK 37 的 `android.app.LocaleManager` 明确提供 `getSystemLocales(): android.os.LocaleList`，`Context.getSystemService(Class)` 与 `LocaleList.get(int): Locale` 签名可用。最小修复计划：DshaApp 首次锁存传入 Application；SystemLanguage 在 Android 13+ 优先经真实 LocaleManager 的 system locales 首项，只有 API 不存在或服务不可用时沿用旧 Resources/Locale 默认值路径；不把 per-app locale 当作 system 源。保留 API 23–32 早锁存和现有 zh/en/system 策略，LanguageController 仍仅重建 UI。纯逻辑测试验证 global zh 与 app en 分离、缺 API 回退和重复初始化不被后续 apply 覆写；新正式包仍需设备复验。

实现：`DshaApp.onCreate()` 把 Application 传给 `SystemLanguage.initialize`；该无 Android import 的 util 通过公开 SDK 方法反射优先读取 `LocaleManager.getSystemLocales().get(0)`，API 缺失/服务不可用时维持原资源与默认 Locale 回退。初始化前可能被 Provider 读取的暂时回退值可被本次权威系统来源覆盖，已完成的锁存不会被后续语言应用覆盖。没有修改 `LanguageController`、语言选择策略或 Web/终端生命周期。新增边界断言覆盖先取到 app-en 暂值后 global-zh 覆盖、API 缺失回退和重复初始化；独立 `javac --release 17`/JUnit 执行 `UiLanguagePreferenceTest` 11 项通过（JDK 25 关闭缓存 JUnit jar 时另打印 AccessDenied 诊断，进程退出码仍为 0）。Gradle 与真机验收留给主代理，新正式包需要验证 Follow system · 简体中文且当前 Web/终端会话不因仅切语停止。

A 独立复核指出此版本尚有源码上可达的发布竞态：线程一在 `tag()` 读到 `cached == null` 后进入慢资源探测；线程二经 LocaleManager 得到 global `zh-CN`，在 `initializeFromSystemTag` 锁内发布 `cached=zh-CN; initialized=true`；线程一随后无条件将旧 app-en 探测结果写回 `cached`，覆盖权威值。旧测试只覆盖顺序读，不能证明该并发交错安全；没有设备证据说明 gate16 就由此竞态触发。限定修复是在 `tag()` 探测之后与初始化共用短锁，发布前复读 `initialized/cached`，让已发布的权威值获胜；不把 Binder 或资源探测包进锁。用闩锁固定“旧探测先开始、权威发布先完成、旧探测最后返回”的顺序作 JVM 回归。

竞态修复：`tag()` 经可注入的纯 Java detector 在锁外完成探测，随后与初始化共用短锁复读 `initialized/cached`；若权威来源已发布，返回其值并丢弃过期探测。`initializeFromSystemTag` 的资源回退探测也移到锁外，仅最后发布持锁。新增 `lateAppLocaleProbeCannotOverwritePublishedSystemLocale` 用闩锁固定旧 en 探测晚于 zh 权威发布，断言该线程返回及最终锁存均为 zh；独立 `javac --release 17`/JUnit 现为 12 项通过。未跑 Gradle 或设备；D07 仍待 gate17 正式包验证。

gate17 首次冷启动补证：global `zh-CN`、同包 per-app `[en]`、偏好 `system`，新系统语言锁存已让维护页中文，受限 Main 设置摘要也显示「跟随系统 · 简体中文」，但 XML/部分字段继续 English（私有 `low17-follow-system-cold.png`），之后平台 per-app locale 仍为 `[en]`。本机 AppCompat 1.6.1 的实际 `classes.jar` 字节码显示，API 33 `AppCompatDelegate.setApplicationLocales` 先调用 `getLocaleManagerForApplication()`；后者只遍历已登记 `sActivityDelegates` 找 Context，空集时返回 null；前者收到 null 就直接返回，不保存待应用值。`DshaApp.onCreate` 的 Application 阶段早于 Activity delegate，因此 `LanguageController.apply()` 虽更新 `UiText` 与 Application Resources，却不能保证此时把平台 per-app `[en]` 改成 zh；`MainActivity.onResume` 又只比较 ConfigStore 实效语言与 `UiText.language`，二者都为 zh，跳过再次应用。这是第二个有源码与设备状态共同支撑的 D07 缺口。限定修复：API 33+ 在 Application 可用的 Context 上直接取得 `LocaleManager`，对仅 zh/en 的解析结果调用 `setApplicationLocales`；低 API 保持 AppCompat 原路径，不把 system 写成空 locale 列表。用注入写入器的纯逻辑测试覆盖“Activity delegate 尚不存在、平台旧 en→zh”、“低 API 走兼容路径”和非法语言拒绝；新包再核 XML/动态文字同语与 cmd locale 实际值。

阶段 2 实施：`LanguageController.apply()` 在 API 33+ 经当前 Application Context 直接取得 `LocaleManager` 并写 `LocaleList(已解析 zh/en)`；API 23–32 仍由原 AppCompatDelegate 路径更新 Activity。纯 `AppLocaleDispatch` 只选择这两个写入器并拒绝 `system/fr` 等非实效语言；其 JVM 测试模拟首次 Activity 尚无 delegate、平台旧 `[en]`，断言平台先写 `[zh]` 再加载 XML 的时序，同时覆盖旧 API 与非法语言。Android SDK 37 的 `LocaleManager.setApplicationLocales(LocaleList)` 与 `LocaleList(Locale...)` 签名已核；独立 `javac --release 17`/JUnit 3 项通过。未运行 Gradle、未操作手机，gate17 旧包的混语证据保持原状。

统一 gate18 的 Release Lint 拦截了 `LanguageController.Api33` 内未在调用点显式保护的两处 NewApi；运行时纯分发的版本条件没有被 Lint 跨回调推导。未安装或交付 gate18。主代理在该平台方法入口增加 `Build.VERSION.SDK_INT < 33` 的明确拒绝，使平台引用同时具备运行时与静态可见边界，低 API 正常调用仍由原 compat 分支承担；不抑制 Lint、不增加 baseline、不跳过检查。下一回执重新验证两版完整门禁。

设备收口进展（尚非整体交付）：gate19 Low 正式同签包已验证上一版保留的应用英文覆盖经本次 Application 初始化改为平台 `[zh]`；`low19-follow-system-cold.png` 的完整 XML 与动态文案一致为中文。Android 可能在覆盖后因服务自动创建 Application，所以 `low19-prelaunch-locale.txt` 是“手动 Activity 启动前”且已经为 `[zh]`，不能把它冒写成旧 `[en]`；旧值证据保留于 gate17 的 `low17-after-launch-app-locale.txt`。同进程原生 English→Follow system 后资源与摘要仍一致，简易终端两次 D07_PID 都为 11038，Web 保留同一鉴权运行；见 `low19-language-live-en/system`、`low19-language-retained-terminal/web` 私有截图。Standard 新候选仍待对应合同，不能由 Low 外推。

最终收口：gate19 Standard同样通过；在DSHA偏好保持system、所有测试会话正常停止后，用正常Android应用locale命令临时设置平台[en]，`standard19-before-overlay-locale.txt`确认为en。确切Standard候选覆盖冷启动后`standard19-after-cold-locale.txt`为zh、完整XML与动态文字一致中文。活会话English→System后简易终端PID19172未变、Web鉴权运行保留；Low对应PID11038。两版新增native-language-follow-system合同均PASS，连同其它14项/版门禁完成正式交付；没有沿用gate16/17失败截图作通过证据。
